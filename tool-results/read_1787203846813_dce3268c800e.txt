    33→
    34→We are building a:
    35→
    36→# Universal Communication OS
    37→
    38→The core thesis is:
    39→
    40→> **Communication should be independent of the network carrying it.**
    41→
    42→A user should be able to express a communication intent without needing to know whether the eventual path is:
    43→
    44→- Matrix
    45→- WhatsApp
    46→- SMS
    47→- Email
    48→- RCS
    49→- Telegram
    50→- Instagram
    51→- Messenger
    52→- another social network
    53→- local Wi-Fi
    54→- Bluetooth
    55→- Wi-Fi Aware
    56→- LAN
    57→- Internet
    58→- another user's device
    59→- a community relay
    60→- an Internet gateway
    61→- a store-and-forward DTN path
    62→
    63→The platform must work both **WITH connectivity** and **WITHOUT Internet connectivity**.
    64→
    65→Internet connectivity should be an optimization, not a fundamental prerequisite for communication between participating devices.

    69→# 2. THE NORTH STAR
    70→
    71→The following principles are immutable unless explicitly changed through architecture governance.
    72→
    73→- Communication is transport-independent.
    74→- Identity is independent of channel.
    75→- Intent is independent of transport.
    76→- Communication Bundles are the fundamental routable object.
    77→- Matrix is the global/federated communication fabric.
    78→- DTN is the offline/edge communication fabric.
    79→- External networks are adapters.
    80→- Gateways connect edge networks to external networks.
    81→- Routing operates over capabilities, policy and resources.
    82→- Applications consume the protocol; they do not define it.
    83→- No single transport is mandatory.
    84→- Internet availability is an optimization, not a prerequisite.
    85→- Offline operation is a first-class architectural requirement.
    86→- Security and privacy are protocol properties, not UI features.
    87→- Architecture changes require explicit approval.

   143→# 4. THREE FUNDAMENTAL PROTOCOL PRIMITIVES
   144→
   145→## 4.1 Universal Identity
   146→
   147→Identity represents the communication entity independently of transport.
   148→
   149→A person is not:
   150→
   151→```text
   152→WhatsApp number
   153→Email address
   154→Phone number
   155→Matrix ID
   156→```
   157→
   158→Those are channel identities associated with a universal identity.
   159→
   160→Conceptually:
   161→
   162→```text
   163→UniversalIdentity
   164→    │
   165→    ├── MatrixIdentity
   166→    ├── WhatsAppIdentity
   167→    ├── SMSIdentity
   168→    ├── EmailIdentity
   169→    ├── TelegramIdentity
   170→    ├── SocialIdentity
   171→    └── DeviceIdentity
   172→```
   173→
   174→Identity resolution must be explicit, authenticated, privacy-aware, and policy-controlled.
   175→
   176→Never make a channel identifier the universal identity primitive.
   177→

   179→
   180→# 5. COMMUNICATION INTENT
   181→
   182→The sender expresses what they want to accomplish.
   183→
   184→Examples:
   185→
   186→- SEND_MESSAGE
   187→- NOTIFY
   188→- REQUEST_RESPONSE
   189→- DELIVER_DOCUMENT
   190→- SEND_MEDIA
   191→- EMERGENCY_ALERT
   192→- SYNC_CONVERSATION
   193→
   194→Intent may contain:
   195→
   196→- priority
   197→- TTL
   198→- maximum cost
   199→- latency requirement
   200→- privacy requirement
   201→- delivery requirement
   202→- payload constraints
   203→- preferred transports
   204→- fallback policy
   205→
   206→The application says:
   207→
   208→> "Deliver this."
   209→
   210→It does not say:
   211→
   212→> "Call WhatsApp API."
   213→
   214→Transport selection belongs to the protocol/routing layer.
   215→
   216→---
   217→
   218→# 6. COMMUNICATION BUNDLE
   219→
   220→The fundamental routable object is a Communication Bundle.
   221→
   222→Conceptually:
   223→
   224→```text
   225→CommunicationBundle
   226→├── bundle_id
   227→├── sender
   228→├── recipient
   229→├── conversation_id
   230→├── intent
   231→├── created_at
   232→├── expires_at
   233→├── priority
   234→├── routing_policy
   235→├── encryption_metadata
   236→├── payload
   237→├── delivery_requirements
   238→└── proofs
   239→```
   240→
   241→Bundles must support:
   242→
   243→- persistence
   244→- deduplication
   245→- expiry
   246→- prioritization
   247→- forwarding
   248→- store-and-forward
   249→- replication policies
   250→- delivery state
   251→- routing metadata
   252→- encryption
   253→- authentication
   254→- integrity
   255→- constrained transports
   256→
   257→A bundle must not inherently depend upon Internet connectivity.
   258→

   261→# 7. MATRIX'S ROLE
   262→
   263→Matrix is the:
   264→
   265→# Global/Federated Communications Fabric
   266→
   267→Matrix may provide:
   268→
   269→- global messaging
   270→- federation
   271→- rooms
   272→- event synchronization
   273→- persistent conversations
   274→- Matrix identities
   275→- Matrix-native communication
   276→- integration with bridges
   277→- application services
   278→
   279→Matrix is NOT:
   280→
   281→- the entire Communication OS
   282→- the universal identity system
   283→- the routing engine
   284→- the offline DTN fabric
   285→- the only transport
   286→- the definition of the application's domain model
   287→
   288→Do not make core protocol abstractions depend directly on Matrix.
   289→
   290→The architecture must allow the system to function without Matrix.
   291→

   293→
   294→# 8. DTN'S ROLE
   295→
   296→The edge network is a:
   297→
   298→# Delay/Disruption-Tolerant Communication Fabric
   299→
   300→It must support:
   301→
   302→```text
   303→store
   304→carry
   305→encounter
   306→forward
   307→store
   308→carry
   309→forward
   310→```
   311→
   312→Potential transports include:
   313→
   314→- Bluetooth
   315→- BLE
   316→- Wi-Fi Direct
   317→- Wi-Fi Aware
   318→- local Wi-Fi
   319→- LAN
   320→- other platform-supported local transports
   321→
   322→The system must support communication where no end-to-end path currently exists.
   323→
   324→Example:
   325→
   326→```text
   327→A
   328→│
   329→│ Bluetooth
   330→▼
   331→B
   332→│
   333→│ Wi-Fi
   334→▼
   335→C
   336→│
   337→│ Internet
   338→▼
   339→Gateway
   340→│
   341→▼
   342→Matrix / external network
   343→│
   344→▼
   345→Destination
   346→```
   347→
   348→The bundle must survive intermittent connectivity.
   349→

   351→
   352→# 9. GATEWAYS
   353→
   354→A gateway connects one communication domain to another.
   355→
   356→Examples:
   357→
   358→- DTN → Internet
   359→- DTN → Matrix
   360→- DTN → SMS
   361→- DTN → Email
   362→- DTN → WhatsApp
   363→- Internet → DTN
   364→
   365→Gateway capability must be explicit.
   366→
   367→A node is not automatically a gateway merely because it has Internet.
   368→
   369→Capabilities must be advertised and policy-controlled.

   377→## Personal Node
   378→

   382→

   384→- mobile
   385→- intermittent
   386→- opportunistic relay

   389→
   390→Stores and forwards bundles.
   391→
   392→## Gateway Node
   393→
   394→Provides access to another network.
   395→
   396→## Edge Node
   397→
   398→Potentially:
   399→
   400→- router
   401→- Raspberry Pi
   402→- PC
   403→- dedicated appliance
   404→
   405→## Service Node
   406→
   407→Examples:
   408→
   409→- Matrix homeserver
   410→- SMS gateway
   411→- email gateway
   412→- external channel gateway
   413→

   415→
   416→Represent capabilities separately from physical device type.

   472→# 12. CHANNEL ADAPTERS
   473→
   474→External networks are adapters.
   475→
   476→Every adapter must conform to a common channel interface.
   477→
   478→Examples:
   479→
   480→- EmailAdapter
   481→- SmsAdapter
   482→- WhatsAppAdapter
   483→- MatrixAdapter
   484→- TelegramAdapter
   485→- InstagramAdapter
   486→- MessengerAdapter
   487→- RcsAdapter
   488→
   489→Adapters translate between the universal communication model and external channel semantics.
   490→
   491→The core protocol must not contain:
   492→
   493→```text
   494→if whatsapp
   495→if telegram
   496→if instagram
   497→```
   498→
   499→Channel-specific behavior belongs in adapters.
   500→

   503→# 13. ROUTING
   504→
   505→Routing is a first-class subsystem.
   506→
   507→It should evaluate:
   508→
   509→- destination
   510→- capabilities
   511→- cost
   512→- latency
   513→- reliability
   514→- availability
   515→- battery
   516→- bandwidth
   517→- storage
   518→- privacy
   519→- trust
   520→- delivery probability
   521→- TTL
   522→- priority
   523→- channel capability
   524→- policy
   525→
   526→Do not build routing around one preferred transport.
   527→
   528→A route could be:
   529→
   530→```text
   531→Bluetooth → Wi-Fi → Internet → Matrix
   532→```
   533→
   534→or:
   535→
   536→```text
   537→SMS
   538→```
   539→
   540→or:
   541→
   542→```text
   543→Matrix
   544→```
   545→
   546→or:
   547→
   548→```text
   549→Bluetooth → Relay → Gateway → SMS
   550→```
   551→
   552→or:
   553→
   554→```text
   555→Bluetooth → Destination
   556→```
   557→
   558→The routing abstraction must permit all of these.
   559→

   561→
   562→# 14. OFFLINE COMMUNICATION
   563→
   564→Offline communication is not an emergency feature.
   565→
   566→It is part of the core protocol.
   567→
   568→The system must support:
   569→
   570→- ONLINE
   571→- DEGRADED
   572→- OFFLINE
   573→- PARTITIONED
   574→- EMERGENCY
   575→
   576→### ONLINE
   577→
   578→Prefer appropriate Internet paths.
   579→
   580→### DEGRADED
   581→
   582→Reduce payload requirements and prefer efficient/reliable transports.
   583→
   584→### OFFLINE
   585→
   586→Use local transports and store-and-forward.
   587→
   588→### PARTITIONED
   589→
   590→Allow messages to remain queued until connectivity opportunities appear.
   591→
   592→### EMERGENCY
   593→
   594→Prioritize small, urgent communication and suppress nonessential traffic.
   595→
   596→---
   597→
   598→# 15. DELIVERY SEMANTICS
   599→
   600→Never use simplistic:
   601→
   602→```text
   603→sent = true
   604→```
   605→
   606→Delivery must be modeled explicitly.
   607→
   608→At minimum:
   609→
   610→```text
   611→CREATED
   612→ACCEPTED
   613→QUEUED
   614→RELAYED
   615→GATEWAY_REACHED
   616→EXTERNAL_ACCEPTED
   617→DELIVERED
   618→READ
   619→```
   620→
   621→Failure states may include:
   622→
   623→- EXPIRED
   624→- REJECTED
   625→- POLICY_BLOCKED
   626→- NO_ROUTE
   627→- CHANNEL_UNAVAILABLE
   628→- GATEWAY_UNAVAILABLE
   629→- DESTINATION_UNKNOWN
   630→
   631→Offline delivery requires distinguishing:
   632→
   633→> "The message left my device"
   634→
   635→from:
   636→
   637→> "The message reached the recipient."
   638→

   640→
   641→# 16. ENCRYPTION AND TRUST
   642→
   643→Relays should not inherently require plaintext access.
   644→
   645→The security model must distinguish:
   646→
   647→- sender
   648→- recipient
   649→- relay
   650→- gateway
   651→- external channel
   652→
   653→A relay should generally be able to forward an opaque encrypted bundle without learning its contents.
   654→
   655→Do not equate:
   656→
   657→```text
   658→transport authentication
   659→```
   660→
   661→with:
   662→
   663→```text
   664→end-to-end confidentiality
   665→```
   666→
   667→Threat-model:
   668→
   669→- malicious relays
   670→- malicious gateways
   671→- replay
   672→- bundle duplication
   673→- Sybil nodes
   674→- spam
   675→- flooding
   676→- resource exhaustion
   677→- identity impersonation
   678→- routing manipulation
   679→- malicious channel adapters
   680→- metadata leakage
   681→- compromised devices
   682→- stale routing information
   683→
   684→Never invent cryptography.
   685→
   686→Use established primitives and libraries.
   687→

   823→- background behavior
